# 首个业务闭环：人员建档、准入与人工赋标

## 目标与范围

以根目录 Spring Boot 应用为代码基础，实现“人工建档 → 对象准入 → 人工赋标 → 查看当前事实与变更记录”。前端源码位于 `web/`，Spring Boot 同源提供页面与接口，业务事实通过 `src/main/resources/domain-pack/` 中的原子 Action 写入 Foundry。

没有人员来源时，人工建档作为可用的业务入口。建档记录明确其人工来源，不伪造外部身份，不按姓名自动合并自然人。同名只提示人工核对；没有身份证明等可靠依据时，不声称已经完成自然人去重。

本阶段包含人员查询、建档、准入、首次人工赋标、追加人工依据/恢复、人工抑制，以及关联事实与操作历史展示。组织与已发布标签目录是前置数据。正式目录缺少发布入口时，应先补齐所需的受控发布能力；本地验收可显式使用合成目录，不将它视为正式业务配置。

自动标签、AI、专项流程、提醒审核发送、外部人员接入、大屏和旧库迁移不属于本闭环。它们的模型继续保留。本规约确定实施顺序，不恢复完整上游复刻目标。

## 现有实现核对

已有模型包含 Person、Organization、ObjectMembership、Tag/TagVersion、PersonTag 和 TagContribution，现有 Action 可以承载本闭环的主要事实变更。无须为页面增加一套独立“人员表”或重复维护一份标签有效状态。

实施前核对发现以下缺口；它们是本轮工作的起点，完成状态及验证见[进度记录](progress.md)，不能把模型测试通过视为应用能力已经完成：

- `FoundryRuntime` 使用内存存储、固定演示身份和全放行 `AuthorizationService`。
- REST Action 的演示 token/角色检查不能替代真实认证，GraphQL 没有同等入口检查。
- 模型计数、审计/outbox 等诊断直接读取可信存储，尚未施加真实数据范围。
- 通用查询没有人员业务投影；对象列表控制器尚未传递前端请求的分页参数。
- `ApplicationService` 会装配自己的 Action 授权器，不能假设传入 `ActionExecutor` 的 Mirror 自定义策略会自动保留。
- JDBC Provider 已有事实、关系、历史、命令回执、成功审计和 outbox 的事务能力；Mirror 尚未接入持久运行模式，也未验证应用重启恢复。

## 页面与操作

| 页面 | 展示内容 | 可执行操作 |
| --- | --- | --- |
| 人员列表 | 姓名、当前组织、准入状态、有效标签摘要；姓名/组织/准入筛选和分页 | 查看详情、人工建档；按权限显示操作入口 |
| 建档表单 | 姓名、当前组织及可选性别/出生日期/入职日期/个人职级/依据/备注 | 校验并确认提交；保存后进入待准入详情 |
| 人员详情 | 基础事实、当前组织、准入决定及依据、标签与来源贡献 | 准入决定、首次赋标、追加人工依据、人工抑制 |
| 准入操作 | 当前状态、目标状态、依据、决定说明 | 显示明确的状态变化并确认；操作人/操作单位来自登录上下文 |
| 人工赋标 | 可选的启用末级标签、当前语义版本、赋标依据 | 首次创建关联或追加人工依据；恢复被抑制标签必须明确告知 |
| 变更记录 | 人员、准入、人员标签与贡献历史，以及相关关系的建立/结束 | 查看操作者、时间、变化与关联命令；按相同数据权限读取 |
| 管理诊断 | 模型、原子 Action、成功审计及 outbox 提交记录 | 仅获授权管理员访问；未接入投递器时明确显示“尚未投递” |

普通业务页面不要求用户填写对象 ID、版本号、贡献键或 Action 名。客户端携带读取时的版本作为并发条件，服务端生成规范身份和命令参数。展示人员准入状态与标签有效性时，使用业务中文说明。

人员详情分别展示“人员已建档”和“已纳入对象库”。PENDING、EXCLUDED、SUSPENDED 的人员仍可按权限查看和追溯，但不能参与有效标签选人。

## 服务命令与原子边界

业务接口拟采用 `/api/mirror/people`，由 Mirror 应用服务校验输入并编排；通用 Foundry REST/GraphQL 继续承担已授权的数据访问，不能成为绕过业务约束的替代写入口。

| Mirror 命令 | 业务输入 | Foundry Action | 同事务结果 |
| --- | --- | --- | --- |
| 人工建档 | 姓名、当前组织、可选基础字段、依据与备注 | `RegisterManualPerson` | 创建 Person、PENDING 的 ObjectMembership、人员归属关系与准入决定组织关系 |
| 决定准入 | 人员、准入预期版本、目标状态、依据代码与说明 | `DecideObjectMembership` | 更新准入事实及决定组织关系；不修改自然人身份 |
| 首次人工赋标 | 人员、标签、读取时人员/准入/标签版本、说明 | `AssignManualTag` | 一次创建 PersonTag、MANUAL 贡献及全部端点关系 |
| 追加依据/恢复 | 已有关联、预期版本、当前标签语义版本、说明 | `ApplyManualTagContribution` | 一次增加人工贡献并解除人工抑制，既有其他来源贡献保留 |
| 人工抑制 | 人员标签关联、预期版本、原因 | `SuppressPersonTag` | 设置抑制事实，保留关联和全部来源证据 |

准入仅支持当前 Manifest 声明的迁移：PENDING → IN_SCOPE/EXCLUDED；IN_SCOPE → SUSPENDED/EXCLUDED；SUSPENDED → IN_SCOPE/EXCLUDED；EXCLUDED → IN_SCOPE。当前 Action 不支持同状态仅更新依据，页面不得提供该操作。以后若确有修正依据需求，再定义相应命令及审计语义。

选择首次赋标或追加依据是 Mirror 的业务职责，但不能在重试时根据新状态悄悄改变原命令。首次命令重放仍执行同一注册 Action、同一参数与幂等键；若另一命令已创建关联，返回冲突并让用户重新确认追加依据。

每个命令只能选择启动时加载并登记的 Manifest，不接受客户端提交 Manifest、CEL、原始 SQL 或任意 effects。参数白名单、非空姓名、合法日期、原因长度和必需证据由服务校验；来源组织、actor、tenant 不信任请求体。

所有写命令要求非空稳定幂等键，绑定真实 actor、命令种类及规范输入。网络重试沿用原键；改变输入需要新命令。同键不同输入拒绝，不用随机新键掩盖失败。版本冲突返回可识别的冲突响应，刷新后由用户重新确认，不自动覆盖。

同一次 Action 内由 Foundry 提交事实、关系、历史、成功审计、命令回执与 outbox。不同命令不宣称共享事务；本闭环不在事务内调用外部系统。成功只表示本地提交，不表示 outbox 已投递。

## 标签有效性与范围

有效标签由当前事实计算，至少同时满足：人员已准入、当前组织有效、标签启用且为末级、PersonTag 未被人工抑制、存在有效来源贡献。贡献的 ACTIVE 状态仍需结合有效起止时间和已发布目录语义处理，不能只判断关联存在。

赋标时在事务内复验人员与准入关联、准入状态、当前组织可用性、标签末级/启用、当前语义版本及预期技术版本。`ApplyManualTagContribution` 当前没有检查人员当前组织有效性，该条件必须在宿主可信事务策略中补齐，或作为明确业务不变量补入 Pack 并测试；不能只靠表单检查。

人工抑制优先于所有贡献。追加人工依据并恢复必须是一条明确操作；规则贡献仍然存在也不能悄悄恢复人工抑制。准入暂停/排除后有效标签停止生效，历史贡献保留。

## 身份与权限

账号是 Mirror 的运行身份，不等同于 Person 或 ExternalIdentity。真实 actor 由 Spring Security 的已认证上下文传递给 Foundry；组织范围由服务端授权配置提供，不接受前端角色选择器、组织字段或自报 actor。

首期采用可替换的本地账号认证适配，凭据以密码哈希配置且不提交仓库，不内置通用默认密码；后续可替换为统一身份源。会话写请求必须处理 CSRF，接口未登录返回 401、无权操作返回 403。本地账号配置修改经应用重启加载生效，旧会话失效；重放也重新校验当前权限。账号热更新与管理页面不在本轮实现范围。

下表是本闭环的最小权限能力划分，并非将原文存在冲突的正式岗位矩阵全部定案：

| 能力 | 数据范围 | 本阶段权限边界 |
| --- | --- | --- |
| 人员查看 | 服务端授予的组织集合 | 列表、详情、搜索、历史、关系、计数遵循同一范围；敏感字段单独授权 |
| 基础档案维护 | 服务端授予的组织集合 | 可以人工建档；拥有标签权限不自动拥有此权限 |
| 人工标签维护 | 授权范围内且符合准入条件的人员 | 可赋标、追加依据、抑制；不能通过它改变人员归属或准入 |
| 准入决定 | 初期仅超级管理员 | 覆盖本闭环状态迁移；普通管理员准入/非对象标记权限待原文冲突确认后再开放 |
| 模型与诊断管理 | 显式管理授权 | 查看通用模型、成功审计和 outbox；普通人员查询权限不自动获得诊断权限 |

组织集合初期按显式授权处理，不自动把“本级组织”解释为“整个组织子树”。片区、下级继承与跨单位代理待确认权限矩阵后再扩展。

安全必须覆盖业务接口、通用 REST、GraphQL（包括别名、多字段、变量与 mutation）、历史/关系和诊断接口。尚未接入相应 Mirror 业务策略的通用写操作默认拒绝；“只隐藏按钮”或“只校验 REST token”不构成授权。

通用只读 `ApplicationService` 的资源授权保留。业务写入选定的装配方式为：Mirror 服务使用固定注册 Manifest 和 `ActionExecutor.withAuthorization(PersonnelPolicy)`，在真实 Action 事务、效果检查及回执重放中检查权限；不通过会替换该策略的 `ApplicationService.execute` 执行这些业务命令。这样复用现有授权扩展，无须修改 Foundry；通用 REST/GraphQL 不开放另一条写路径。

授权测试包括普通业务入口和替代入口，不使用全放行策略来证明业务权限成立。拒绝/失败记录由 Mirror 安全日志记录 actor、命令、原因与 trace，不记录密码或完整敏感参数；它们与 Foundry 成功审计明确区分。

## 持久化与初始化

本地开发先接入已有 JDBC Provider，以独立 H2 文件库验证重启恢复。配置支持显式的数据目录和数据源；不使用旧 `.runtime/mirror.mv.db`，不把新 Pack 自动加载到旧库。H2 只作本地验证，国产目标数据库选定后单独验证方言、锁、精度、迁移及恢复，不将 H2 测试当作国产库验收。

演示内存模式与持久运行模式必须显式区分。合成目录/人员初始化需显式开启，仅首次空库初始化，留下初始化标识；重启不得重新赋标、重置准入或覆盖已有事实。界面标明合成数据，正式启动不得自动创建虚构人员。

启动加载 Pack 后检查 Schema 绑定；模型不兼容时明确失败，不自动丢弃或重建存储。重启必须恢复当前事实、关系、历史、成功审计、命令回执与 outbox，并保证重放不重复提交。暂不启动真实外部投递器。

## 验收场景

1. 人工建档成功后，只产生一个 Person、一份 PENDING 准入记录及完整归属关系；相同命令重试返回原结果，审计/outbox 不增加。
2. 同名人员允许区分保存，界面提示核对；系统不自动生成未经确认的外部身份。
3. PENDING 人员不能赋标。超级管理员确认准入后，首次赋标一次性创建关联、MANUAL 贡献及全部关系。
4. 追加人工依据保留既有贡献；人工抑制使标签失效；明确恢复操作解除抑制，历史可追溯。
5. 暂停/排除准入后有效标签不再参与当前筛选，原有证据仍可按权限读取。
6. 停用组织、停用/非末级标签、错误语义版本、伪造操作组织、旧技术版本均拒绝，未提交任何部分事实、成功审计或 outbox。
7. 仅查看身份不能写；标签维护身份不能建档或决定准入。跨组织读取/写入在业务、REST、GraphQL、关系/历史及诊断路径均不可绕过。
8. 账号撤权或人员移出授权范围后，旧幂等命令重放也拒绝；同键不同输入拒绝。
9. 两个页面基于同一旧版本操作，后提交的冲突清晰可见，不自动覆盖；首次关联并发竞争不会留下孤立贡献。
10. 应用停止并重启后，人员、准入、赋标、关系历史、actor、成功审计和 outbox 均保留；原命令重放没有第二份提交。
11. 人员列表分页、筛选和计数只基于有权查看的人员，不泄露范围外人数；敏感字段遵守字段授权。
12. 业务页面提供空状态、提交中/失败/冲突提示，防止重复点击；桌面和移动宽度可操作，错误不丢失待确认的输入。
