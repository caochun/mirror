# 页面术语与原始需求的对应

重新检索根目录两份 DOCX 的正文和表格后确认：

- 《原始材料-“政务系统对象库项目”试点工作方案》中未出现“准入”和“授权组织”这两个说法。
- 《政务系统对象库-软件需求规格说明书》中有“对象准入”条目，原文为：“现有用户系统中的有效用户默认纳入对象库，人员身份和当前组织均以现有用户系统为准。”
- 同一需求书的“片区管理员”定义中有：“使用明镜明确授权组织集合及其下级组织作为数据范围……”

这些词在需求书中描述的是对象范围和数据访问范围，不等于页面必须使用相同按钮名称。原文也没有定义名为“办理准入”的审批工作流。当前人工建档后的待确认状态，来自没有现成人员来源时的应用实施选择，不能说成原文强制要求。

## 页面用词

| 内部概念或旧文案 | 当前页面表达 | 含义 |
| --- | --- | --- |
| 对象准入 / ObjectMembership | 对象库管理状态 | 该人员是否纳入对象库管理，独立于登录账号和来源状态 |
| 办理准入 | 调整管理状态 | 管理员确认或调整范围，不暗示另有审批流程 |
| PENDING / 待准入 | 待确认 | 尚待确认是否纳入对象库管理 |
| IN_SCOPE / 已纳入 | 正常管理 | 当前属于管理对象 |
| SUSPENDED / 已暂停 | 暂停管理 | 暂停相关对象库业务，不代表停用登录账号 |
| EXCLUDED / 已排除 | 非管理对象 | 不属于当前对象库管理范围，档案和历史保留 |
| 全部授权组织 | 全部可查看单位 | 当前账号有权查看的单位，不代表全市所有单位 |
| 授权范围共 N 人 | 可查看人员共 N 人 | 当前筛选下可见人员数量 |
| 人工抑制 | 取消标签 / 已人工取消 | 人工令该人员的标签不生效，保留来源依据与历史 |

原文“非对象账号”基于已有账号系统假设；当前模型区分自然人与登录账号，因此页面使用“非管理对象”，避免让人误以为在禁用账号。

本次调整页面表达，不改动 ODL 枚举、Action 名称、现有数据和权限范围。当前本地账号仍按显式单位集合授权，尚未自动实现原文片区/下级单位的继承授权；不能通过改文案宣称这一权限能力已完成。

## 对象关系入口

管理员在人员详情点击“对象关系”，或从“对象浏览”选择其他类型。页面首先展示业务名称、说明和相关信息；原始关系名、方向箭头、ID 和建立时间收进“技术详情”。历史关联和变更记录继续保留。

关系读取依据 Pack 的全部关系类型，包含入向和出向，不要求对象事先声明 `@link` 导航字段。点击关联对象可继续浏览，顶部路径可返回先前对象；技术属性保留在折叠区域中。

这些管理视图当前仅向管理员开放，未扩大普通账号的数据权限。后端通过 Foundry 存储接口读取关系，端点对象投影和关系历史继续使用 Foundry ApplicationService；不会为展示而修改 Pack 或重建历史。

## 按业务对象表达含义

侧栏、页标题、浏览路径和关联链接使用同一套业务描述。例如任职记录显示“演示人员001的任职 · 综合管理（党政办公室）”，正文说明“演示人员001在党政办公室担任‘综合管理’岗位，目前在任”，相关信息分别列出人员、任职单位和岗位。

管理状态记录显示“某人的管理状态”，人员标签显示“某人的某标签”，赋标依据显示人员、标签和依据类型，标签目录读取当前发布版本的实际名称。关联信息缺失或不可访问时明确显示待确认，不根据名字或 ID 推测。

关系名称以当前浏览对象为视角：从人员看是“当前任职”，从任职看是“人员”；从人员看是“所属单位”，从单位看是“本单位人员”；从人员标签看是“赋标依据”，从依据看是“对应的人员标签”。关系条数仅作为页脚辅助信息。

人员标签描述复用现有生效判断，不把“关联仍存在”解释为标签有效。查看历史关联时，页面注明关联对象显示当前信息；历史状态仍从独立变更记录查看，不冒充历史时点的完整快照。
