# 待用户确认的模型决定

旧代码已删，新 Pack、分层定义、模型和 Action 已验证。现有应用已成为根目录的标准 Spring Boot 项目，Domain Pack 随应用资源打包。现已实现首个人员闭环、独立 JDBC-H2 持久库及本地账号/组织授权；实际证据与未验收边界见[进度记录](../development/progress.md)。未改旧数据库，原文业务分歧仍按下表处理。

## 已按本轮指示修订的总体设计

1. 人员、组织、岗位、任职、来源档案与身份是基础事实；标签、事项风险、提醒/审核/回执为上层业务事实。都可由Foundry保存，计算和业务流程留在Mirror。
2. 自然人ID长期稳定；ObjectMembership单独记录准入；ExternalIdentity仅映射自然人来源身份。单位/岗位独立，个人职级与岗位等级、当前组织与任职分开，变化均可追溯。
3. PersonTag.suppression单独保存人工抑制，TagContribution保存依据；当前有效性为服务计算结果，不再维护presence或leaf的第二份权威状态。
4. 当前发布版本以关系选择；审核与发布、投递和撤回独立。AudienceSnapshot冻结名单/发送约束，批准后内容修订复用该名单；TaskRecipient不因修订重建。
5. Mirror身份/权限服务独立于人员事实；不假设有旧明镜账号技术栈，也不把密码、会话、worker租约等都建成本体对象。
6. 配置编辑草稿在Mirror持久工作区，发布后的标签/策略/示例版本才进入Pack；运行日志/普通HTTP失败不都建成本体。当前Pack已声明14个原子Foundry Actions；Mirror只编排流程，不向Foundry注册整个流程。必要的动态事务边界见action-boundaries.md，尚未实现的不当作已支持。可表达模型不等于规则已实现。

以上模型修改及沿用现有应用的方向已获授权；这不自动确认下面的原文分歧，也不代表完整业务系统已实现。

## 后续实施边界

根据确认范围，先定义Mirror命令输入、权限矩阵与接入契约，再选择业务闭环实现顺序。只有出现阻塞该闭环的Foundry通用正确性问题才改底座；不恢复完整上游逐项重制。

如需保留旧业务数据，先另做迁移设计，不能直接将本Pack加载到`.runtime/mirror.mv.db`。外部鹿路通契约、国产目标数据库、网络/身份条件仍须单独确认和验收。
