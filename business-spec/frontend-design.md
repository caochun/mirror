# Mirror 前端业务与页面设计草案

状态：业务分析与页面建议，尚未实现。日期：2026-09-26。

本稿重新对照《原始材料—“政务系统对象库项目”试点工作方案》和《政务系统对象库—软件需求规格说明书》，以业务目的、权限和状态规则为依据，不继承其中关于既有明镜技术栈、菜单或部署方式的假设，也不以当前 Java 原型的行为作为验收标准。

文中“试点方案”指前者，“需求书”指后者。页名、路由、布局和交互组织均为设计建议；业务规则以所列章节为依据。原始 DOCX 按仓库约定不提交。

## 1. 对业务的重新理解

试点方案的目标是“动态建档、精准画像、分类提醒、闭环管控”。日常使用者实际在完成六件事：

1. 确认管理范围内有哪些人、目前在哪个单位、担任什么职务，哪些基础信息可靠。
2. 判断哪些人符合某类教育提醒条件，纠正标签遗漏、误判和过时信息。
3. 围绕日常履责或具体事项形成接收名单，选择合适的提醒内容。
4. 由创建单位本级的独立审核员确认名单和最终内容。
5. 了解消息是否送达、最新内容是否被阅读，对异常和逾期分别处理。
6. 追溯当时依据、内容版本、名单、审核和实际发生的事件。

基础对象、组织关系与业务记录分开：人员档案回答“这个人是谁、当前在哪里、过去如何变化”；标签、事项和提醒回答“这次为什么关注、做了什么”。标签不是风险定性结论，“无标签”不是“无风险”。

Foundry 支撑对象、关系、时间和变更追溯。前端将其表达为档案、任职履历、赋标依据、版本对比和操作时间线。日常业务导航按工作组织，通用对象类型名、关系 ID、事务 ID 不进入普通操作流程。

党委、纪委、职能部门是责任分工；超级、片区、单位管理员及审核员是权限职责。这两组概念不能直接互相替代，不据此建设三套独立内容库。

| 问题 | 原始依据 | 本稿处理方式 |

## 3. 两个使用端与角色工作台

管理端为 PC 工作台；接收端为鹿路通嵌入的独立移动 H5。两端共享已审核内容的展示规范，入口、权限和可见数据分别设计。

| 使用者 | 默认首页 | 高频工作 | 权限界限 |
| --- | --- | --- | --- |
| 超级管理员 | 全市工作台 | 数据质量、标签体系、映射规则、AI批次、内容示例和全市提醒 | 可配置全局业务；创建任务仍走独立审核，不能凭超级权限自行通过 |
| 片区管理员 | 授权范围工作台 | 范围内赋标、AI复核、创建提醒、异常与未读查看 | 授权组织根集合及其下级取并集 |
| 单位管理员 | 单位工作台 | 本单位及下级人员标签、提醒、督促 | 任意层级单位及全部下级；当前组织影响创建单位 |
| 推送审核员 | 待我审核 | 阅读冻结内容、检查名单分布、通过或驳回 | 仅创建单位等于本人当前单位；无独立人员库浏览职责，不审核下级任务，不审核自己创建的任务 |
| 接收人 | 本次提醒详情 | 查看本人的最新审核发布内容 | 仅本次正文，不看到标签、内部风险、名单、审核或管理入口 |

管理端顶部固定展示当前操作单位、数据范围摘要、账号和后台任务入口。账号角色来自真实授权，不提供演示式角色切换器。账号支持多组织上下文时，切换单位应提示未保存草稿，并重新校验列表、选人范围和操作权限。

| 导航 | 页面与建议路由 | 主要目的 |
| --- | --- | --- |
| 工作台 | `/workbench` | 展示待办、范围和异常入口 |
| 人员与组织 | `/people`、`/people/:id`、`/organizations/:id` | 查人、看档案与组织关系、定位数据问题 |
| 标签工作 | `/tagging`、`/tag-reviews`、`/tag-issues` | 日常人工赋标、AI复核、局部异常处理 |
| 提醒管理 | `/reminders`、`/reminders/new`、`/reminders/:id` | 创建、审核跟踪、发送、修订和撤回 |
| 审核工作台 | `/reviews`、`/reviews/:id` | 审核员专用待审队列和快照详情 |
| 送达与阅读 | `/receipts`、`/overdue` | 分别处理送达异常、未读和逾期 |
| 统计分析 | `/analytics` | 对象、标签覆盖、提醒与渠道统计下钻 |
| 配置与治理 | `/settings/tags`、`/settings/mappings`、`/settings/content`、`/data-issues`、`/jobs`、`/audit` | 全局配置、数据质量、异步批次与审计 |
| AI助手 | `/assistant` | 超级管理员组合查询与业务入口跳转 |
| 接收端 | 独立 H5 `/r/...` | 本人提醒阅读，具体票据路径由正式契约决定 |

菜单按真实权限裁剪。审核员仅呈现审核队列、审核详情和本人审核记录。组织目录是业务对象的只读视图；账号授权维护是单独的管理职责。

## 5. 工作台：把待处理的工作放在首页

首页优先展示待办清单，统计卡片帮助定位，不采用大屏式图表堆叠。

- 管理员：AI待复核、标签无法计算、人员关联异常、我的驳回任务、即将过期的审核、发送失败和逾期未读。
- 审核员：本单位待审任务，优先提示临近计划发送时间的任务，展示提交人、人数、提交时间和审核时限。
- 超级管理员：额外显示规则重算和AI批次进度、全市覆盖缺口、渠道及H5异常。

每项待办都带范围、更新时间和可跳转的筛选条件。同一异常在多个页面的入口指向同一记录，避免出现重复处理台账。

## 6. 人员与组织：当前事实和业务历史并置

依据：需求书3.1、2.2；试点方案全员建档要求。

人员列表采用左侧组织树、右侧筛选与表格。筛选包括姓名、组织、人员状态、档案关联状态、标签条件；列表展示姓名、脱敏身份、当前单位、职务摘要、标签数和异常摘要。默认展示有效对象，停用与非对象记录通过状态筛选查看。

异常要说明影响，而不是只有红色图标。例如“缺少出生日期：年龄类标签无法计算”“缺少身份证号：不能正式推送，仍可人工赋标”。字段局部异常不能把整个人所有功能都禁用。

点击姓名先打开档案摘要抽屉，完整档案使用独立页面：

| 页签 | 展示内容 | 关键交互 |
| --- | --- | --- |
| 基础档案 | 当前组织、当前职务、基础字段、数据来源和最近同步时间 | 源信息与业务备注区分；敏感字段按独立权限查看并审计 |
| 组织与任职 | 当前归属、兼任职务、历史任职及调动时间线 | 显示生效时间、结束时间，必要时展开“系统记录于” |
| 当前标签 | 按因人、因事分组的有效标签 | 来源、版本、依据、操作组织和生效时间；人工删除及恢复入口 |
| 提醒记录 | 本人接收的有权查看的任务 | 任务创建单位、当前版本、送达及阅读信息分别展示 |
| 变更记录 | 标签与关系的增删改、人员状态变化 | 前后对比，区分业务生效时间和系统记录时间 |

“当前标签”和“待复核建议”使用不同区域，不能将AI候选画成已生效标签。历史查询支持选择时间查看授权范围内的状态，但历史权限仍由服务端判断；人员调动后不自动把其全部历史任务暴露给新单位。

组织详情展示性质、上下级、当前人员、业务覆盖和相关提醒。来源数据尚未接入时显示“未接入/待同步”，不把它当作0人。

## 7. 标签工作：人员操作与全局配置分离

依据：需求书3.2。

### 7.1 人员赋标工作台

保留组织树和人员表格，右侧展示选中人员的标签信息。单人显示完整标签；批量展示“全部已具备/部分具备/均不具备”和人数，不能把部分具备误显示成全部选中。

批量选择必须区分“本页已选”与“全部筛选结果已选”。跨页选人保留选择状态，范围变化后提示重新确认；服务端重新检查对象资格和权限。提交后展示新增、已存在、跳过及失败人数，失败可定位到人员。

操作称为“添加标签”“删除当前标签”“恢复标签”。备注可选，不增加材料上传和额外审核。人工删除提示“后续规则重算不会自动恢复”，操作面向人员的逻辑标签，不让管理员理解或选择底层来源关系。

### 7.2 AI建议复核

待复核清单以“人员 + 候选标签”为单位，展示本次使用的资料摘要、建议理由、批次和生成时间。支持确认、拒绝和查看档案；未经复核的候选不进入选人条件。

AI调用失败、无法判断、规则无法计算分别成类，显示原因和处理入口。资料或标签定义已变化时提示建议过时，并在确认时由服务端复核。AI复核属于日常管理员工作；批次创建、候选配置与提示词维护只对超级管理员开放。

### 7.3 标签配置

左侧最多三级目录，右侧“定义 / 自动规则 / AI辅助 / 覆盖情况 / 版本历史”。允许二级末节点赋标，父节点用于分类与统计。

新标签默认人工赋标。规则采用业务字段、运算符、值、全部/任一条件组的表单。发布前展示预计新增、失效、不变、无法计算人数及明细入口；确认后启动后台重算。AI配置发布不自动开始评估。

“新提拔干部”“退休过渡期干部”按需求书本期采用人工维护，不强制填写日期、不设置自动到期、不开放AI或自动规则。成长特质可并存，职务层级按最高层级保留，岗位领域可多选。

目录停用提示受影响规则、人员和历史引用；已使用的标签保留历史。映射页面明确“仅影响赋标，不改变组织主数据”。

## 8. 提醒创建：持续可见的名单与最终内容

依据：需求书3.3、3.4。

建议使用四步向导，底部固定“保存草稿 / 上一步 / 下一步”，最后一步主按钮为“提交审核”。

```text
选择接收人员 → 编辑提醒内容 → 设置发送与阅读时限 → 预览确认并提交审核
```

### 8.1 选择人员

页面上部在“条件筛选 / 指定人员”间切换，下部或右侧始终保留同一份接收名单。

- 条件：多个组织取并集，组织与标签取交集，多个标签显式选择满足任一或全部。
- 指定：按姓名、单位、部门、职务检索，手工加入名单，与条件结果叠加后按人员ID去重。
- 已选摘要：总人数、组织数、条件命中人数、额外指定人数、排除人数；重叠人员单独解释，不把两类人数直接相加。
- 名单支持检索、逐个移除、查看已排除人员及恢复；条件重新计算不得悄悄恢复手工移除的人。
- 停用、非对象、身份或当前组织不唯一等人员展示排除原因；缺少出生日期等局部字段不因此整人排除。
- 进入下一步确认人数；仅1人时明确“本次向1人定向提醒”。名单或条件变化后确认失效。

跨页选中结果由服务端维护或解析，不能只发送当前浏览器加载的那一页。前端人数是预览，提交审核时服务端复验并冻结；若发生变化，展示差异并要求重新确认，不能静默删人。

### 8.2 编辑内容

左侧编辑标题和受控正文，右侧手机效果预览。可从启用的内容示例中选择，也可直接撰写；示例选择器按适用标签推荐，最终由人选择。

引用示例后提示“已复制为本次任务草稿”，修改不回写示例。支持文字、列表、受控HTTPS链接、JPG/PNG图片；每张不超过2MB、最多6张。本期不提供视频、音频、附件、答题和表单工具。

预览使用服务端清洗后的结果，与H5共享内容展示规则。上传失败、图片加载失败、链接校验失败分别显示。图片逐张确认不含内部敏感信息；图片替换后原确认作废。

### 8.3 时间与时限

仅提供“审核通过后立即发送”和“指定时间单次发送”。阅读时限显式选择24、48、72或168小时，说明按每个人首次实际送达成功时间起算。

显示创建单位和本级审核员配置状态；没有有效审核员时保留草稿并解释不能提交的原因。定时时间已过且尚未通过审核时，不允许补批准发送，应重新设时并发起新审核轮次。

### 8.4 最终确认

同屏展示最终内容、组织人数分布、排除明细、链接校验、逐图确认、阅读时限、计划时间、创建单位和重复提醒提示。重复提醒显示重复人数及上次发送时间，允许再次确认继续，不与网络幂等混同。

提交冻结的内容和名单就是审核和发送的依据。标签后续变化不能重算这份历史名单；待审核期间只读，修改前先撤回本轮审核。

## 9. 任务详情与审核：围绕同一份快照

任务列表展示标题、创建单位、创建人、目标人数、计划时间、当前状态、待审轮次与最近操作。点入详情后以“概览 / 接收记录 / 内容与审核 / 操作历史”组织。

审核页面是独立工作界面：左侧完整内容和手机预览，右侧人数、单位分布、时限、时间、确认信息及审核操作。审核员只能读取本次审核所需的快照信息，不能因此获得完整人员档案权限。驳回填写意见；通过弹窗说明“立即开始后台发送”或“等待计划时间”，避免按钮语义误导。

| 状态 | 管理员主要操作 | 审核员主要操作 |
| --- | --- | --- |
| 草稿/已驳回 | 编辑、提交审核 | 无 |
| 待审核 | 查看、撤回本轮审核 | 本单位且非本人创建：通过、驳回 |
| 审核过期 | 重新设时、重新提交 | 查看，禁止迟到批准 |
| 已审核待发送 | 查看；定时未发送可填写原因取消 | 查看审核记录 |
| 发送中 | 查看作业进度 | 查看审核记录 |
| 成功/部分失败/失败 | 查看；仅失败或未知重试；按权限修订、撤回 | 查看审核记录 |
| 撤回中/部分撤回/撤回失败 | 查看逐人结果，仅失败或未知项重试撤回 | 查看审核记录 |

已发送内容修订使用专门页面，只开放标题、正文、图片和链接，名单与时限锁定。详情同时显示“当前发布版本”和“待审修订版本”；新版本批准前，接收人继续看到原发布版本。

新版本发布时重置最新版本阅读状态，保留首次送达时间和原截止时间。例：截止时间为9月26日10:00，修订在当天11:00发布，则尚未阅读新版的接收人立即满足逾期条件；不能为其自动延长一天。

旧版本内容和阅读事件只能从有权限的审计入口追溯，业务阅读统计始终面向最新发布版本。撤回需要原因，逐人展示结果，不能点击后就把所有记录画成成功；H5根据有效撤回状态停止返回正文。

## 10. 送达、阅读与逾期

依据：需求书3.5、3.6。

接收记录表分列展示“渠道状态”和“最新版本阅读状态”，并包含当前组织、发送时组织、提交时间、首次成功送达时间、截止时间、首次阅读时间、最近失败原因。

允许“渠道结果未知 / 最新版已读”的组合：先认可真实阅读，同时提示对接不一致。不能把送达成功数减去已读数直接视为所有未读人数。

未读和逾期清单以任务接收记录为行，姓名、当前主管单位、手机号、任务、截止时间和状态同屏展示；另显示去重人数，避免一人多任务导致人数混淆。当前单位用于主管组织督促，发送时单位用于解释历史分布，两种口径明确标注。

不提供“代标已读”“手工解除真实逾期”“完成整改”等按钮。阅读当前版本后自动解除当前逾期状态，历史保留；再次提醒进入新任务创建流程，不能无人确认自动重发。首期不采集线下督促记录、不提供未读清单导出。

异常中心分为身份关联、规则计算、AI、鹿路通、H5及回执不一致。每项说明影响、发生时间、关联对象与处理入口：数据缺失回到权威来源治理，渠道故障重试失败或未知对象，H5故障恢复后重新打开即可，不重新群发。

## 11. 接收端 H5

独立移动单页：标题、业务约定的发布信息、最新审核发布正文和必要提示。页面固定提示“本提醒仅向本人展示，请勿截图外传”。

必须设计的状态：身份校验中、正文加载中、正常正文、票据失效需从鹿路通重新进入、无权访问、正文加载失败可重试、提醒已撤回、图片加载失败占位。

身份有效且正文渲染成功后记录当前版本首次阅读，重复进入不覆盖时间。图片单独加载失败不阻塞已读，但记录图片异常。阅读回执上报失败与正文显示失败分开处理，采用幂等重试，不虚假宣称服务端已记录成功。

不增加“我已阅读”强制按钮、停留计时、滚动完成率或考试等业务。H5不携带管理菜单、内部标签、其他人员信息或可枚举名单；访问他人链接不能查看正文。正式身份票据和免登交互仍依赖鹿路通契约。

## 12. 统计与 AI 助手

统计采用“人数摘要 → 分布 → 可下钻明细”。显示数据时间、组织范围、任务版本和指标口径，点击统计数字带条件进入业务清单。人员总量和标签覆盖按人员去重；多标签覆盖率不能简单相加。

AI助手仅向超级管理员开放。回答附组织、时间、标签和状态等解析条件，返回人数、来源及明细入口；“问操作/问口径”引用需求原文，歧义口径先说明差异。

“给这些人发提醒”返回“创建提醒草稿”动作卡，携带查询条件进入同一创建向导，再经确认、提交审核和独立审核。动作卡不能调用发送或直接将任务设为发送中。

## 13. 视觉与交互原则

建议蓝白、中性灰、紧凑而可读的桌面工作台；颜色主要用于层级、选中和状态。状态同时有文字，不能只靠颜色表达；不按标签数量给人员打分或绘制廉洁指数。

- 表格支持分页、固定关键列和批量摘要；5万人员不一次加载到浏览器。
- 人员摘要、标签依据用抽屉，长内容编辑和审核用独立页面，少量确认用弹窗，避免多层弹窗。
- 长任务离开页面后继续，任务中心显示进度、成功/失败/跳过数、原因及部分重试；提交成功不等于执行成功。
- 空数据、尚未接入、无权限、加载失败使用不同提示。时间显示到秒并注明展示时区。
- 列表返回保留筛选、分页和上下文；组织切换、对象调动或授权变化后重新校验。
- 文本与控件保持可辨识对比度，表单支持键盘操作，错误贴近对应字段，表格不靠悬浮提示承载唯一解释。
- 所有关键人数、资格和可执行操作由服务端校验；前端隐藏或禁用按钮只是交互反馈。

## 14. 专项事项工作台：从试点目标出发的后续建议

试点方案的阶段性标签需要对应某一件具体事务。例如同一个人可能同时参与A项目招标与B项目验收，阶段性标签应能回答“哪个项目、什么角色、哪个阶段、为什么赋予、何时结束”。

建议未来页面为“事项列表 → 事项详情”，详情包括事项概况、阶段、参与人员及角色、内部风险依据、专项标签、关联提醒和时间线。工作结束时结束本事项对应的关系和标签，不影响另一事项及长期性标签。

项目开始前、进行中、结束后均可选择相关人员创建提醒，仍复用统一审核和送达流程。行权平台提供风险线索，本系统展示来源和处理状态，不默认扩展为监管模型开发平台或案件办理系统。

这是试点总体目标的页面延展；需求书本期专项范围、对接字段、阶段变更来源与授权尚需澄清，不能作为已经实现或验收的功能。

## 15. 设计与验证顺序

1. 先原型化一条贯通流程：人员列表 → 档案 → 人工赋标 → 选人 → 编辑 → 审核 → H5阅读 → 未读/逾期查看。
2. 用两类管理员和独立审核员演示权限差异，覆盖跨组织、调动和历史任务查看。
3. 补齐规则发布、AI复核、局部异常、任务修订、撤回和异步失败。
4. 再完善统计、AI助手、配置治理，以及专项事项的范围评审。

原型验收至少包括：

- 缺少出生日期仍能处理不依赖年龄的标签；缺少身份证号可人工赋标但不能正式推送。
- 条件选人叠加指定人员、手工移除后重算、跨页全选都不丢失或偷偷增加名单。
- 无本级审核员不可提交，自审与下级任务审核不可执行，定时审核过期不可补发。
- 示例更新、人员调动、标签变化都不修改已冻结的审核与发送快照。
- 修订审核期间旧发布版仍可阅读；新版发布后重置已读但不延长截止时间。
- 渠道未知与有效阅读可同时存在；正文失败不记已读，个别图片失败按文档规则处理。
- 手工删除标签后自动重算不能恢复；AI待复核不能参与正式名单筛选。
- 有效当前版本阅读解除逾期，管理员不能代读；已撤回H5不再展示正文。

这些是后续前后端联合验收用例，尚未全部通过。现有 `tasks.md` 的勾选和内存原型测试不足以证明上述业务完成。

## 16. 前端对后端的契约要求

页面通过 Mirror 业务接口访问 Foundry，不允许浏览器任意写底层对象绕过业务规则。接口应提供带权限的人员列表与档案、名单预览及确认版本、冻结任务快照、审核决策、异步作业进度、独立渠道/阅读状态、敏感字段审计访问和H5本人内容。

重要写入携带并发版本及幂等标识；提交确认绑定名单与内容版本。人数变化、授权变化、过期审核、旧版本操作等返回明确业务冲突，页面展示原因并刷新，不静默覆盖。

当前 Java 原型与需求存在需要先修正的差距，尤其是独立审核和真实授权、送达与阅读分离、修订保留截止时间、AI动作卡只负责跳转条件，以及完整分页和名单语义。前端设计不应迁就这些原型限制。
