# 完整业务应用交付计划

2026-09-26 用户明确设立目标：完成完整业务应用，前端采用 React + Tailwind。

## 交付目标和边界

Mirror 是基于独立 Foundry 平台开发的具体业务应用。交付包括可启动服务、关系数据库持久化、管理端、独立接收端H5、真实认证授权、业务API、后台作业和部署说明。React + Tailwind 是用户确定的前端要求；建议配套 TypeScript、Vite、React Router、Vitest/Testing Library 与 Playwright，实际版本通过锁文件固定。

Foundry 保留通用对象、关系、历史、事务和事件职责；政务规则、UI和渠道适配留在 Mirror。浏览器调用受控业务API，不能直接写Foundry对象以绕过业务校验。Foundry需要修正时在其仓库独立提交，再更新子模块指针。

需求依据为两份原始业务文档及 [frontend-design.md](frontend-design.md)，代码原型与此前已勾选清单不构成已验收证据。不存在已可复用的明镜技术栈，登录、组织及授权都必须明确实现或接入。

## 首批必须修正的不变量

1. 审核员不拥有全市人员读取权限；单位范围包含全部下级，片区为授权根集合及下级的并集。
2. 权限来自真实身份和服务端授权；创建任务、审核、名单及敏感查看逐次校验。
3. 无本级有效审核员不得提交，创建人与审核人不同；草稿不能直接变成发送中。
4. AI动作卡仅携带条件到创建向导，不能直接更改任务发送状态。
5. 送达与阅读是独立维度；合法阅读不依赖渠道回执先到达。
6. 修订只改变内容，新版发布重置阅读状态但不改变原名单、首次送达时间或截止时间。
7. 人工删除逻辑标签会抑制自动恢复；不能靠改一个来源记录而允许另一个规则重新赋标。
8. 查询和批次不能只处理默认100条；统一实现正确分页、筛选和人数口径。

## 外部依赖与范围决定

- 国产关系数据库是生产目标。开发数据库及Mock结果明确标注；真实数据库的一致性和性能验收保留单独任务。
- 鹿路通正式契约、身份票据、签名及撤回结果未提供时，先完成可替换适配和故障Mock；不得声称真实送达已验收。
- AI服务需要明确模型入口及数据约束；无真实模型时可完成接口和确定性测试替身，不将固定数据标成AI结果。
- 原始数据和组织来源、生产认证提供方需要明确；开发演示数据与生产接入分别配置，不生成虚假的上游跳转。
- 阶段性专项工作、逾期短信、非对象权限和统计口径见前端草案的范围差异。先推进独立于这些决定的本期闭环，再完成范围确认。

外部依赖不阻止独立工作推进，也不能作为提前宣布整个目标完成的理由。交付报告逐项区分完成、Mock验证、真实环境验证和待接入。

## 完成门槛

详细清单以 [tasks.md](tasks.md) 为准。勾选需有实现和对应验证；禁止仅凭方法存在、静态页面、配置模板、少量内存测试或伪造成功状态宣称完成。

本地验收应能从空环境按说明启动，经过真实登录，完成管理端和H5贯通流程；页面包含空、失败、无权、并发冲突、异步处理中等状态。持久化重启、权限拒绝、任务快照、历史审计和幂等都要验证。生产外部契约与国产库环境的验证边界须明确。

持续目标保持 active，按里程碑实现、验证和提交推送。没有用户要求不暂停目标；只有满足完整验收门槛才标记 complete。
